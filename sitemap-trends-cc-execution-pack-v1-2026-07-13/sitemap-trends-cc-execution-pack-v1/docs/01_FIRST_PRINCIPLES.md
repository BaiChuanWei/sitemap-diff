# 01｜第一性原理

## 原理一：真正的产品数据是“变化事件”

Sitemap XML 只是来源。真正需要保存的是：

- 哪个站点
- 哪个 Sitemap Endpoint
- 在什么时间
- 新增、删除或恢复了哪个 URL
- URL 是否是游戏详情页
- URL 对应哪个游戏实体
- 该游戏新增了几个独立来源域名

## 原理二：采集失败不能转化为业务变化

以下情况只能记录为失败，不能产生新增或删除：

- 403、404、429
- 请求超时
- DNS 失败
- 空响应
- HTML 冒充 XML
- XML 截断
- Gzip 损坏
- 子 Sitemap 部分失败
- URL 数量异常下降
- 数据库事务失败

最近一次成功数据必须保留。

## 原理三：首次运行只建立基线

首次接入一个站点时，已有的全部 URL 都属于 baseline，不属于今日新增。

只有第二次及后续成功运行，才能计算 `added`、`removed` 和 `restored`。

## 原理四：趋势按独立域名计算

同一游戏在同一域名出现多个语言页或多个 URL，趋势只增加一个来源域名。

URL 可以保留多条，但域名计数不能重复。

## 原理五：不确定的实体匹配必须审核

游戏名称匹配分级：

- `exact`：完全确定，可自动合并
- `high`：高置信度，可自动合并并保留证据
- `medium`：必须进入人工审核
- `low`：创建独立候选，不自动合并

## 原理六：最小闭环优先

第一版先确保：

```text
100 站稳定检查
→ 每日新增 URL 正确
→ 数据可导出
```

趋势榜、页面美化和备用采集不能阻塞主闭环。

## 原理七：每个阶段必须独立验收和回滚

不得一次性同时大改数据库、采集器、前端和部署。

每个 Milestone 必须有：

- 输入
- 输出
- 修改范围
- 禁止范围
- 测试
- Commit SHA
- 回滚方式
