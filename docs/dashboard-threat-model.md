# Sitemap 监控本地控制面板 —— 威胁模型（M0）

状态：设计阶段（M0）。适用范围覆盖 M1-M6 全部规划功能，但 M1 本轮只实现只读部分，很多控制点在 M1 阶段"设计已定、代码未触发"（例如没有写接口就不存在 CSRF 风险，但 CSRF 保护机制仍在 M1 就位，供 M2 直接复用）。

## 1. 攻击面与信任边界

本应用是**单用户本地工具**，威胁模型的核心假设是：
- 唯一可信来源是运行本机浏览器里、由本工具自己提供的页面。
- 不信任同一台机器上其它进程/网页发起的跨源请求（防 CSRF/DNS rebinding 类攻击）。
- 不信任局域网内其它主机（服务只绑定 `127.0.0.1`，物理上局域网请求到不了）。
- 信任服务端读取的本地文件（`config/*.csv`、SQLite 数据库）——这些本来就是本机用户自己维护的配置，不做"防用户自己"的沙箱化处理，但要防止**页面上的用户输入**通过接口间接篡改到不该改的文件路径。

## 2. 具体威胁与对策

| 威胁 | 场景 | 对策 |
|---|---|---|
| 局域网/公网访问 | 别人访问 `http://<你的内网IP>:8766` | `server.listen(port, '127.0.0.1')`——只绑定回环地址，物理上局域网请求无法到达 |
| CSRF（跨站请求伪造） | 用户打开的恶意网页向 `127.0.0.1:8766` 发起写请求 | 服务启动时生成一次性 CSRF token（写入响应给前端页面，前端所有写请求带上 `X-Dashboard-Token` header）；同时校验 `Origin`/`Referer` 必须是 `http://127.0.0.1:<port>` 自身，两者任一失败即拒绝（403）。M1 无写接口，此机制仅搭好骨架供 M2 起的写接口直接使用 |
| DNS rebinding | 攻击页面把域名解析改到 127.0.0.1 后发起同源请求绕过 Origin 检查 | 额外校验 `Host` 请求头必须精确等于 `127.0.0.1:<port>`（不接受任意 Host 名） |
| XSS（存储型） | 网站的 Sitemap 里出现恶意 `<script>` 之类的 URL 或页面标题被插入 HTML | 前端渲染 URL/标题一律走 `textContent`/DOM API 赋值，不使用 `innerHTML` 拼接用户数据；服务端也不对用户数据做"净化后当 HTML 输出"的假设——净化只在浏览器端展示层用 DOM API 完成 |
| 任意文件读取/路径穿越 | 导出接口如果接受用户传入的文件名/路径 | 导出接口只接受 `run_id`（校验为已知格式，比对 DB 中真实存在的 run_id），不接受任意文件系统路径；文件名由服务端根据 `run_id` 拼出，不回显用户输入片段到路径中 |
| Shell 注入 | 如果诊断接口把 site_id 传给 shell 命令 | 面板的 `POST /api/sites/:site_id/diagnose`（M2 起）直接调用 `diagnoseSite()` JS 函数，不经过 `child_process`/shell，不存在注入面 |
| 请求体过大导致内存耗尽 | 恶意/异常大 POST body | 所有写接口限制请求体大小（如 1MB），超过直接 413 拒绝，不读入内存后再校验 |
| 非法 Content-Type | 用非 JSON 的 body 打 API | 写接口强制要求 `Content-Type: application/json`，否则 415 |
| 重复点击/双开始 | 用户连点"开始监控"，或两个标签页同时点 | M3 复用 `src/lock.js` 的 `collector.lock`；面板内存态运行控制器（RunController）在拿锁前先做一次内存级"是否已有进行中任务"检查，双重防护 |
| stale lock 阻塞 | 上次进程被杀死留下的锁 | 复用现有 `acquireLock` 的 PID+存活时间校验，无需新逻辑 |
| SSE 连接耗尽 | 大量标签页/刷新循环打开 SSE | 限制单进程最大并发 SSE 连接数（如 20），超过时新连接收到明确错误而不是被无限接受 |
| 服务被杀死后遗留 `crawl_runs.status='running'` | 面板进程在采集中途被强制结束 | 服务启动时检测数据库中 `status='running'` 且明显早于当前时间的 `crawl_runs` 行，标记为"异常中断"（只读展示提示，不擅自改写历史数据，改写逻辑留给用户在 UI 里确认后触发的显式操作，M3+ 设计） |
| 端口冲突误判 | 端口被非本项目服务占用 | `/api/health` 返回固定 `service` 字段用于识别"是不是我自己"；不是则不复用，直接报错 |
| 磁盘空间不足 | 导出/写库时磁盘满 | 捕获 `ENOSPC` 等错误，向用户展示清晰的中文错误提示，不吞异常，不产生半写文件（先写临时文件再原子替换的模式贯穿配置写入和导出） |
| 中文/Windows 路径 | 项目部署在含中文的路径下 | Node 侧已用 `node:path`/`fileURLToPath`，无 ASCII-only 假设；PowerShell 脚本文件本身以 UTF-8 with BOM 保存（Windows PowerShell 5.1 对无 BOM 的 UTF-8 中文字符串有渲染乱码风险），脚本内路径变量一律加引号包裹 |

## 3. 明确不做的事（本轮/近期）
- 不做用户认证/多用户隔离——单用户本地工具，回环绑定本身就是主要边界。
- 不做 HTTPS——回环地址上的本地明文 HTTP 是本地开发工具的标准实践（浏览器不会因此报警告），引入自签名证书反而增加"用户需要点掉证书警告"的困惑。
- 不做速率限制/防爬——本地单用户场景不存在外部滥用者。

## 4. M1 阶段风险敞口小结
M1 只有只读 GET 接口和 SSE 心跳，没有任何状态变更能力，因此本轮实际风险敞口仅剩：
1. 绑定地址错误导致意外对外暴露（用测试断言 `server.address()` 的 host 是 `127.0.0.1`）；
2. 只读接口本身如果拼接了不受信任的输入到 SQL（应使用参数化查询，与现有代码库风格一致）；
3. 静态文件服务如果允许路径穿越读取 `public/dashboard/` 之外的文件（限制静态服务只映射到该目录，规范化路径后校验前缀）。
